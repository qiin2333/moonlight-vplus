# 协同振动验证：原神攀爬触击

## 三模块边界

生产链为 `GameRumblePipeline` 串联以下三层，Android 协调器只接入设备发现、线程、
偏好与传输；原生 DS PCM 和扳机通道继续独立。

1. `RumbleSignalTracker`：按主机流维护电平、因果包络、正向残差、最近变化的时间、
   有符号增量与 revision。`sample` 接收主机输入，`advance` 仅推进时间；重复电平、
   ticker 与重连回放不创建新 revision。TEST 不进入 HOST 历史。
2. `GameRumbleAllocator`：纯函数把特征和可用输出能力变成两端计划。当前兼容策略集中
   在分配器：机身低通道瞬态 0.25、高通道瞬态 1、高通道持续 0.30，手柄保留 HOST。
   这些是折叠前增益，不代表物理能量比例，也不把支持 CLICK 等同于能可靠接管瞬态。
3. `RumbleOutputRenderer`：执行计划，负责来源混合、输出槽限频、去重与单马达折叠；
   真实 `DeviceVibrationCoordinator` 继续负责强度、量化、租约及音频/触摸占用。

本轮是结构重构，未重新启用实测无改善的“机身仅瞬态”方案，也未启用新的原语接管。
未来校准后的分工应修改分配策略和相应渲染后端，无需按游戏场景添加判断。

`GameRumblePipelineTest` 直接使用生产管线、渲染器与真实机身 worker，注入时钟、
调度队列和最终输出回调。覆盖收敛、重复脉冲、过期脉冲、多人隔离、TEST 插入、重连、
音频占用恢复与停止。该组测试将 worker 普通电平间隔设为 0，以隔离线程实际等待；
250ms 冷却和抢占仍由现有 `DeviceVibrationCoordinatorTest` 单独验证。

## 已知现象与范围

本地 DS 手柄的原神攀爬反馈是一拍一拍的 click，机身模拟路径则有“嗡一下”的感觉。
这个对比说明需要验证每拍的起振、结束和静默间隔，不能仅提高振幅。
原生 DS 触觉与串流收到的双通道 rumble 不一定是同一信号；本修改不声称恢复原生 HD 波形。

## 本次软件保证

- 包络按上一段保持的输入推进；重复包、相同时间戳和额外 ticker 不会改变时间积分。
- 瞬态收敛时先输出严格终态，再停止 ticker，避免小残差被最低振幅放大为持续底振。
- 起振按边沿安排，停止替换待执行电平；不会在收到停止后补播已结束的脉冲。
- 移除 60ms 观察窗口。机身的起停边沿绕过普通电平的 250ms 冷却，持续电平替换仍受限。
- 手柄始终保留全部 HOST 信号；点击能力位不再触发 25% 高频让渡。

这不保证零物理延迟：主线程调度、通信延迟及已阻塞的 Binder 无法被抢占。
如果 worker 尚未执行起振就收到停止，过期脉冲会被丢弃，不排队补播。
原语支持只记录能力；本次没有把每个 rumble 起振自动映射为 PRIMITIVE_CLICK。

## 真机比较（待执行）

保持同一攀爬路线、帧率、机身强度和握持方式，关闭音频派生触觉及触摸反馈干扰。
分别比较本地 DS、串流纯手柄、串流仅机身、协同模式，记录系统版本、机型、连接方式
及 `Device haptics tier` 日志。不要把测试得到的主观强度当作线性振幅等价。

1. 连续攀爬十步：每拍能否分清，拍间是否安静；立即停止攀爬，是否还有底振。
2. 持续低频振动后静止：机身补偿最终必须归零；高频持续的少量补偿仍是当前策略。
3. 连续快速起停及长时间攀爬：检查 vendor 服务无卡死、ANR 或堆积后的补播。
   250ms 保护保留在持续电平替换上，频繁起停的厂商兼容性需要单独验证。
4. 在支持的设备上，用独立测试程序对比直接 PRIMITIVE_CLICK、短 one-shot、完整游戏路径。
   点击原语必须先确认支持，并使用相同机身设置。这个 A/B 工具不包含在本次修改中。

若原语清脆但 one-shot 发闷，后续评估独立的点击补偿后端；若直接播放正常但整条路径
发闷，继续检查调度。需要同步采集 HOST 两通道及最终 vibrate/cancel 时间，才能区分
输入本来就是宽脉冲还是输出将其拉长。采集应使用临时诊断构建，避免长期逐包日志开销。

## 自动化回归

运行 `./gradlew :app:testNonRootDebugUnitTest`。覆盖重复包、长静默后起振、独立通道复位、
终态归零、27ms 脉冲、过期脉冲、停止抢占电平冷却、会话结束以及音频/触摸所有权恢复。
这些用例证明软件时序性质，不代替上述真机触感和厂商服务验证。
